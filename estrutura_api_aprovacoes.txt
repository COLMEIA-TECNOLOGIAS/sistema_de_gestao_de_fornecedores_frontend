ESTRUTURA LÓGICA PARA IMPLEMENTAÇÃO NA API (BACKEND)
====================================================
Funcionalidade: Aprovação de Exclusões (Fornecedores e Pedidos de Cotação) por Administradores.

Esta estrutura descreve como o backend (API) deve ser preparado para processar os pedidos de exclusão dos técnicos em vez de excluir os registos directamente.

1. NOVA TABELA DE BANCO DE DADOS
--------------------------------
Tabela sugerida: `pending_deletions` (ou `exclusoes_pendentes`)

Campos sugeridos:
- id (Primary Key, Integer/UUID)
- item_type (String/Enum): Define o tipo de item a ser excluído. Ex: 'supplier' (Fornecedor) ou 'quotation_request' (Pedido de Cotação).
- item_id (Integer/UUID): O ID original do item que se deseja excluir na respectiva tabela.
- item_name (String): O nome ou título do item (útil para o frontend exibir rapidamente sem necessidade de JOINs).
- requested_by (Integer/UUID): O ID do usuário (Técnico) que solicitou a exclusão.
- technician_name (String): O nome do técnico (opcional, também por conveniência na exibição).
- status (String/Enum): 'pending' (pendente), 'approved' (aprovado), 'rejected' (rejeitado). O padrão é 'pending'.
- created_at (Timestamp)
- updated_at (Timestamp)

2. ALTERAÇÕES NOS ENDPOINTS DE EXCLUSÃO EXISTENTES
--------------------------------------------------
Endpoints afectados:
- DELETE /api/suppliers/{id}
- DELETE /api/quotation-requests/{id}

Nova Lógica de Negócio (nos Controllers):
- Quando a requisição chegar, deves verificar o nível de acesso (role) do utilizador autenticado.
- SE (user.role == 'admin'):
    - Exclui o item normalmente da base de dados.
    - Retorna status 200 OK ou 204 No Content.
- SE (user.role == 'technician' ou não-admin):
    - NÃO exclui o item.
    - Cria um novo registo na tabela `pending_deletions` com status = 'pending'.
    - Retorna status 202 Accepted (ou 201 Created), opcionalmente com uma mensagem indicando que a acção foi enviada para aprovação do Administrador.

3. NOVOS ENDPOINTS A SEREM CRIADOS
----------------------------------
A. Listar Pedidos Pendentes
   - Rota: GET /api/pending-deletions
   - Permissão: Apenas Admin
   - Retorno: Uma lista contendo todas as exclusões com status 'pending'.
   - Uso: O frontend usa esta rota para mostrar o contador vermelho na Navbar e exibir a lista dentro do modal.

B. Aprovar Exclusão
   - Rota: POST (ou PUT) /api/pending-deletions/{id}/approve
   - Permissão: Apenas Admin
   - Lógica:
       1. Busca o pedido na tabela `pending_deletions`.
       2. Verifica o `item_type` e localiza o registo na tabela real.
       3. Executa a exclusão real (apaga o fornecedor ou o pedido de cotação original).
       4. Atualiza o status em `pending_deletions` para 'approved'.
       5. Retorna sucesso.

C. Rejeitar Exclusão
   - Rota: POST (ou PUT) /api/pending-deletions/{id}/reject
   - Permissão: Apenas Admin
   - Lógica:
       1. Busca o pedido na tabela `pending_deletions`.
       2. Atualiza o status para 'rejected' (ou apenas apaga o registo de `pending_deletions`).
       3. O item original no sistema permanece intacto.
       4. Retorna sucesso.

4. INTEGRAÇÃO FINAL COM O FRONTEND
----------------------------------
Actualmente, o ficheiro `src/services/api.js` contém um objecto chamado `pendingDeletionsAPI` que simula estas operações usando `localStorage`.

Assim que criares e testares as rotas na API (backend):
1. Vai até `src/services/api.js`.
2. Altera os métodos de `pendingDeletionsAPI` (getAll, requestDelete, approve, reject) para usarem chamadas `api.get()` e `api.post()` direccionadas às tuas novas rotas.
3. Remove todo o código que menciona `localStorage` dentro dessas funções.
